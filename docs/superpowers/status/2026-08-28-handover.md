### 高德接口的真实行为（三条推翻了原判断）

**1. 步行 API 不支持 `waypoint` —— 参数被静默忽略**

```
无 waypoint  6920 m
带 waypoint  6920 m   ← 完全一致，说明参数无效
```

`route_engine.py:59` 一直在传这个参数。**无 Key 时走兜底逻辑，这个 bug 被掩盖了**；
配上 Key 后 `api.py:82-87` 的候选循环会返回和基准完全相同的路线 → 绕行恒为 0 → 打分失去意义。
只有驾车 API 支持途经点，步行没有。

解决方案已实测可行 —— **两段拼接**（`起点→POI` + `POI→终点`）：

```
基准        6920 m / 5536 s / 278 折线点 / 13 段指令
两段拼接    6897 m / 5517 s / 280 折线点 / 18 段指令
```

折线沿真实街道、转向指令连续、绕行真实。代价是每个候选要 **2 次**调用而非 1 次。

**2. 步行调用平均 4.84 秒 —— 比预估慢得多**

实测 6 次串行 = 29.0 秒。按现在的 N+1 结构：10 个 POI = 11 次 ≈ 53 秒；
改成两段拼接 = 21 次 ≈ 100 秒。而前端 `api.js:19` 是 20 秒 abort → **必然失败**。
所以「候选截断」不是优化项而是必须项。

**3. 类别名不用改（原判断错误，已作废）**

实测 `餐饮|景点|购物` 与 `餐饮服务|风景名胜|购物服务` 都返回 20 个 POI，高德接受模糊匹配。
且旧过滤词 `['餐饮','景点','购物']` 对新类别名命中 20/20 ——
因为高德返回的 type 是 `餐饮服务;中餐厅;特色/地方风味餐厅` 这种带分号的串，`in` 判断成立。
**这条从优化清单里删除（原 P1-3 的后半部分）。**
