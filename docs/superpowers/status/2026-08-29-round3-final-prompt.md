## S0｜图上有标记明显不在路线上（确认缺陷，根因是 400 米 + 图例不分类）

**现象**（用户截图，`大连海洋大学黑石礁校区 → 东北财经大学`，漫游模式）：
图上三个亮点标记，1 和 3 贴着折线，**2 号横向飘出约三四百米**，在另一个街区上。
图例把三个统称「沿途亮点」，用户的结论是「途经点不在地图路线上面」。

**根因（两处叠加，都要改）**

1. `api.py:64 NEARBY_POI_METERS = 400`。`_collect_highlights` 里
   `highlights[0]` 是被选中的 POI，路线两段拼接真的穿过它；但 `:203-217` 补进来的
   第 2、3 个只要求「距推荐折线 ≤ 400 米」。400 米在演示的缩放级别下横跨两个街区，
   「沿途会经过」这句话在图上立刻破功。代码注释（`:63-65`）把 400 米解释为
   「约等于步行 5 分钟的绕行」—— 那个尺度是给**列表文案**定的，画到图上就不成立。
2. `MapView.vue:189` `iconFor(isActive ? 'poi-active' : 'poi', ...)` —— 只区分
   「有没有被点击」，**不区分「路线真的经过」和「在旁边」**。三个标记同款同色、
   编号连续，图例（`:291`）只有一项「沿途亮点」。

**改法**

- `NEARBY_POI_METERS` 从 400 收到 **150**。超过就不进 `pois`（图上和列表都不出现）。
  这会让某些真实路径只剩 1 个亮点 —— **可以接受**，注释里已有的原则是
  「宁可只返回一个亮点，不在这句话上注水」，照它执行，不要为了凑三个放宽阈值。
- 图上把第一个标记（真途经点）和后面的**视觉区分开**：新增一种 kind（比如
  `waypoint`），沿用包豪斯配色体系里已有的色板，不要新造一个色。
  图例拆成两项：**「途经点」**（路线经过）和**「附近亮点」**（在旁边）。
- 卡片列表里同步区分：第一张标「途经」，其余标「附近」。配合 S2 显示真实米数后，
  用户自己就能看出 1 号是 2 米、2 号是 130 米。

**验收标准**
- 三场景九组合 + 至少一条**非演示表**的真实路径（用户那条 `大连海洋大学→东北财经大学`
  就行，`AMAP_KEY=` 屏蔽后走兜底也要验一遍），`pois` 里每一项的真实
  `point_to_route_meters` 都 ≤ 150。
- 后端断言：把 `NEARBY_POI_METERS` 临时改成 400 → 有点名断言变红（说明这个阈值被守住了）。
- 前端断言：第一个 POI 的标记 className 与后续不同；图例渲染两项。
- **截图自证**：一张图上能看出「途经点」和「附近亮点」是两种标记。

## S1｜三个模式必须看得出区别（根因：演示数据只有 2 个 POI 且挨在一起）

**现状（已查实）**：`poi_explorer.DALIAN_POI_SCENARIOS` 每个场景**只有 2 个 POI**：

| 场景 | POI 数 | 两点间距 |
|---|---|---|
| dut→xinghai | 2 | 约 1300 m |
| donggang→laohutan | 2 | **约 40 m** |
| xianlu→fujiazhuang | 2 | 约 1800 m |

`_choose_candidate` 的 `DETOUR_APPETITE = {"+5": 0.6, "+15": 0.2, "roam": 0.0}`
逻辑本身是对的，但**候选池里只有 2 个点，三个模式不可能选出三个不同结果**。
donggang 两点相距 40 米，`+15` 和 roam 的 polyline sha1 完全相同
（`e546e9979430`），这是你上一轮如实报告过的「2/3」。

**还有一个连带后果**：`detour_minutes` 现在三场景九组合**全部为 0**
（距离改成从几何量出来之后，真实绕行只有 2~34 米，不足一分钟被 `round()` 抹平）。
所以「额外时间」格恒显 `+0`，三个模式在那个格子上完全一样 —— 用户投诉的
「三个模式没区别」现在主要就是这个格子造成的。

**改法（三件事一起做，缺一不可）**

### (a) 换掉三个演示场景，选步行合理的距离

现在三条演示路线是 **92 / 98 / 98 分钟**的步行 —— 没人这么走，而且 7 公里的图上
40 米绕行只有一个像素。用现有六个地标算出的可选组合（`road ≈ 直线 × 1.25`）：

| 组合 | 路网距离 | 步行 |
|---|---|---|
| **xinghai→fujiazhuang** | 4115 m | **51 min** |
| **xinghai→xianlu** | 4418 m | **55 min** |
| laohutan→fujiazhuang | 6095 m | 75 min |
| dut→xinghai（现用） | 6978 m | 86 min |

前两条明显更适合步行演示。但**四公里仍偏长**，评委看不出 5 分钟绕行。
所以：**新增两个更近的地标**，凑出三条 **1.5～3 公里（20～35 分钟）** 的演示路线。
建议在星海广场 / 西安路一带补 2 个真实地标（比如星海公园、马栏河、软件园）——
坐标必须是真实的 GCJ-02 经地理编码得到再用 `coord.gcj02_to_wgs84` 转成 WGS-84，
和现有六个地标同一套流程，注释里保留 GCJ 原值便于核对。**不许拍坐标。**

三条演示路线的目标形态：
- 一条 **最短对比型**：绕行极小，用来当「基准」的直观参照
- 一条 **中等绕行型**
- 一条 **明显绕行型**：`roam` 下能看出肉眼可辨的岔路

### (b) 每个场景的兜底 POI 补到至少 4 个，且**离线距离要拉开**

这是三个模式能分开的**必要条件**。每个场景的 4 个 POI 应当形如：

| POI | 离基准线距离 | 谁会选它 |
|---|---|---|
| A | ~20 m | +5（顺手一绕） |
| B | ~120 m | +15 |
| C | ~300 m | roam（随便走走） |
| D | ~80 m | 陪衬，进「沿途亮点」列表 |

评分要交叉安排（不能让最远的那个同时也是最高分，否则三个模式又会一致选它）——
让 `score - appetite × off_route/100` 这个排序键在三个 appetite 下产出三个不同赢家。
**做完先用下面的探针自证，再写测试。**

POI 名称和评分**必须是真实存在的店**（沿用现有 `DALIAN_POI_SCENARIOS` 的取数方式：
实测数据）。位置可以在真实店址里挑符合上表距离分布的，**不许编造一个不存在的店**，
也不许给真实店编一个假坐标。如果真实店凑不出 300 m 那一档，就把 roam 那档降到
实际能达到的最大值，并在测试里断言实际值，**不要为了凑数字造假**。

### (c) 让「额外时间」格恢复信息量

`detour_minutes` 为 0 是真实的（绕行确实不到一分钟），不要去伪造它。改前端：
`ResultView.vue:71` 已经在 detour 为 0 时把说明文案换成「几乎不耽误，顺路就到」，
但大字仍是 `+0 分钟`。改成 **detour 为 0 时大字显示距离增量**（`+13 米`），
单位跟着变。这样几何是真的、数字也是真的、三个模式还能看出差别。

做完 (a)(b) 之后如果三条新场景的 detour 天然 ≥ 1 分钟，这条就自动不触发，保留兜底逻辑即可。

**验收标准（硬性，逐条自证并把实测值贴进报告）**
1. 三条演示路线的基准步行时长都在 **20~40 分钟**。
2. 每个场景三个模式的 `polyline` sha1 **3/3 互不相同**（不再允许 2/3）。
3. 每个场景三个模式选中的 POI **两两不同**（不只是 +5≠roam）。
4. 基准→推荐的最大分离在三个模式下**单调递增**：`+5 < +15 < roam`，
   且 roam 至少 **150 m**（用真实店址能达到的值，达不到就报告实际上限）。
5. 「额外时间」格在三个模式下显示三个不同的值。
6. 现有 `test_mode_differentiation.py` 的单调性断言从
   `separations["roam"] > separations["+5"]` 收紧成三段单调
   （`+5 < +15 < roam`）—— 现在这条能在 `+15 == roam` 时通过。

## S2｜「距路线约 N 米」是错的数字（确认缺陷，与 S0 同源）

**现象**：POI 卡片上的「距路线约 70 米」和真实距离对不上，而且**两个 POI 的数字是对调的**。
实测 dut→xinghai `+15`：

```
POI 甲  真实距路线   1.6 m   卡片显示 70
POI 乙  真实距路线  24.2 m   卡片显示  7
```

**根因**：`poi["distance"]` 是高德 `place/around` 返回的**「距搜索采样点」**的距离
（`poi_explorer._normalize_amap_poi` 原样透传），而 `PoiCard.vue:89` 把它标成
「距路线约」。两回事。`_collect_highlights`（`api.py:186`）其实**已经算出了**
到选中折线的真实距离（`point_to_route_meters`），算完却扔掉了，没写回 POI。

采样点是按里程 25%/50%/75% 取的三点之一，所以这个数字既不是距路线、也不是距起点，
对用户没有任何意义，而且会随采样点漂移 —— 两个 POI 数字看起来对调就是这么来的。

**改法**：`_collect_highlights` 把算出来的距离写进返回的 POI，
键名用 `off_route_meters`（和 `_evaluate_candidate` 里已有的命名一致，别再造一个）。
被选中的那个 POI 也要算（它现在是 `highlights[0]`，走的是另一条路径没算过）。
前端 `PoiCard` 读新键，读不到时**不显示这一行**，不要退回显示旧的 `distance`。
`distance` 字段可以保留在响应里（别的地方可能读），但前端不再拿它当「距路线」。

**验收标准**
- 卡片显示的米数与 `point_to_route_meters(poi.location, route.polyline)` 的
  四舍五入值一致，三场景九组合全部核对。
- 新增后端断言：`highlights` 每一项的 `off_route_meters` 与独立算出的真实距离相等
  （含 `highlights[0]`）。破坏验证：把写回那行删掉 → 该断言变红。
- 前端断言：`off_route_meters` 缺失时不渲染这一行，且**不回落到 `distance`**。

## S3｜「重新规划」加模式选择

**现状**：`App.vue:55 onReplan()` 已经在用 `request.mode` 原地重发，
基础设施都在了，只差一个让用户改 mode 的入口。

**改法**：结果页「重新规划」旁边给三个模式的切换（复用 `EXPLORE_MODES`
和首页那套 `+5 / +15 / 漫游` 卡片样式，别新造一套视觉），当前模式高亮。
点击某个模式即以该模式原地重发：`onReplan(nextMode)`，
`api.recommendRoute({ ...request, mode: nextMode })`，成功后
`selectedRoute.value = { ...result, request: { ...request, mode: nextMode } }`
—— **`request` 里的 mode 必须跟着更新**，否则再点一次「重新规划」会退回旧模式。
`originLabel` / `destinationLabel` 照旧保留，别让第二次响应把标题的地名冲掉。

切换期间 `:disabled="replanning"`，文案「重新规划中…」，失败走已有的
`bh-notice--error` + `role="alert"`。**不要回首页。**

这条做完，评委可以在同一条路线上连点三个模式看差异 —— 这是 S1 效果的最佳展示方式，
所以 S1 的验收标准 2/3/4/5 应当在这个交互上肉眼可见。

**验收标准**
- 结果页点 `+15`，停在结果页，标题地名不变，指标和折线随模式变化。
- 连续切三个模式，三次的折线肉眼可辨不同（**截图三张自证**）。
- `request.mode` 每次都更新（断言：切到 roam 后再点重新规划，发出的仍是 roam）。
- 破坏验证：把 `request` 的 mode 更新那行去掉 → 有点名断言变红。
